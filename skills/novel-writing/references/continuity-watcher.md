# 连续性监视者

监视者是本次任务内的归档和查阅角色。它不在后台运行，不监听外部文件变动，不擅自改正文。档案存放在小说项目，不放进 Skill 安装目录，也不混用不同小说或分支的档案。

## 启用与归档

1. 用户要求启用时，使用指定的故事档案；未指定且项目中没有明确档案时，可在小说项目根目录用 `story-bible.md`，遇到同名无关文件或多个项目时先确认。初次建立可用[故事档案模板](../assets/story-bible-template.md)，只从作者指定的材料和范围建档。既有档案按需补栏目，不另建一份相互竞争的档案。
2. 默认只在用户要求写入时更新档案。用户明确要求持续维护本书时，在档案头记下维护方式与范围；在以后实际调用本 Skill 的写作任务中，章节经作者确认采用后才更新该档案。「只审不改」「不要落盘」优先于持续维护。明确要求关闭持续维护时，仅将档案的维护方式改回「仅按请求更新」；若当前禁止写入，则停用本次并说明未能保存停用状态。维护授权不扩展到正文、其他档案或分支。
3. 每次只读新确认或重写的章节、现有相关条目及必要来源。把同一事件记在事件表一次，用稳定编号（如 `E-007`）关联人物和伏笔。出处用章号与场景、短锚点或项目相对路径，并记录采用稿本。只收录未来选剧情、查冲突或回收伏笔用得上的内容：

   - **人物**：将身份和别名放在索引；目标、处境、关系和知情情况等会变化的信息另记。每条只记一个状态项的变化、生效章和场景、变化后的状态及出处。归档顺序不是生效顺序；不要用新状态覆盖旧状态。已有档案只有「现状」而无法定位时间时，保留为旧摘要，不把它当成历史状态。
   - **事件**：时间、谁参与、发生了什么及造成什么后果；只把正文确立或作者明确确认的内容列为事实。
   - **伏笔**：关联人物或事件、埋设处、未回收／推进中／已回收／作废、变化所在章或场、揭晓限制及实际回收出处。区分人物已知与读者已知；最早揭晓章或触发条件只填作者已确定的约束。可能是伏笔的细节放入待确认，不擅自给普通细节定性或揭晓答案。
4. 归档结束后更新已核对章及版本，只标实际核对的范围，缺口明确列出。对采用的文件稿记下[文件指纹](#文件版本核对)，只为实际读过并据以更新档案的版本登记。重复归档同一版时更新原条目，不重复记账。试稿不推进已归档进度；只有用户要求留存时才单列待确认。采用替换稿时，刷新本章相关条目，标出受影响的旧状态、伏笔和后文依赖；未核对的记为待复核，不改后文正文。

## 续写先查档案

1. 先确定小说、分支、接续点及作者要求。按[稿本选择规则](continuity.md#分清不同版本)确定采用稿，再用[续写取样](story-craft.md#续写取样)读接续段。用[按需查阅](archive-lookup.md)从档案取覆盖概况和当前场景实际依赖的几条记录；已知编号时直接按编号取。不要用主角名或「伏笔」把整片档案读进来。
2. 对每个状态项，只取在接续点前已生效的最后一条已确认记录；同章看场景或锚点的先后，倒叙看场内故事时间。伏笔是否已铺设或回收、读者是否知情，按正文读到接续点的顺序判断，不借用后文。核对所选记录及其实际依赖的原文版本，不核对无关章节。指纹一致、记录无矛盾且够用时，不打开旧章正文做重复确认。只有已改文件、缺章、矛盾、待复核或缺证的关键条目才定点回查；未复核不得当成事实。
3. 切到掌握秘密的视角或写到待回收线索时，按[知情与揭晓规则](continuity.md#分开角色与读者所知)核对，勿因人物知情而提前揭晓。看不出改动文件是否仍是采用稿时，按稿本选择规则处理。新稿本若明确采用，以原文为准；档案没获写入授权时只在本次写作中纠正，不保存变更。仍无法确认的关键情节，不据此推进，必要时问一个问题。用户只要正文时不附档案或核对报告。

## 文件版本核对

对保存到本地的采用稿，用[版本核对脚本](../scripts/check_chapter_versions.py)计算 SHA-256。每份源文件单独记项目相对路径和指纹；多章共用文件时，指纹只能证明文件是否变了，不能确定具体改了哪一章。首次归档时核对指纹对应实际阅读的稿本；若读取期间文件有变动，重新确认，不给旧摘要补上新指纹。

在项目根目录调用脚本；`<脚本>` 替换为脚本路径，`<指纹>` 替换为档案记录的 64 位十六进制值。`--expect` 可重复，批量核对本次涉及的源文件：

```text
python <脚本> snapshot chapters/03.md
python <脚本> check --expect chapters/03.md <指纹>
```

脚本只读取明确列出的文件，输出路径和版本结果，不输出正文。`unchanged` 只证明文件没变，不代表档案没有漏记；`changed`、`missing` 和 `unreadable` 都不能作为已核对。对聊天稿件、没有指纹的旧档案或不能运行脚本的环境，记为未比对，只回查本次必要且可取得的原文或请作者确认，不假称版本一致。
